## 2. 已准备的实现

第 0 期使用“每人一份整本手账快照”验证接入能力。正式版仍按逐条目标、大事记和资金记录设计，不能把本阶段快照当成已经完成第 1 期同步。

- `supabase/migrations/20261005083216_phase0_journal_sync.sql`：使用官方 CLI 的 `migration new` 生成文件，再写入表、权限、触发器和保存 RPC。
- `public.user_journals`：用户 ID 是主键，同时引用认证用户；按用户归属开启 RLS。匿名角色没有读取或执行保存 RPC 的权限；其他登录用户只能看自己的快照。
- `save_journal`：从认证上下文取得用户身份，接收预期版本和操作 UUID。使用行锁与服务端版本校验，旧版本返回冲突及云端当前快照。重复请求沿用同一操作 ID、同一内容，不增加版本；同一 ID 换内容会拒绝。
- 服务端管理版本号和更新时间。写入触发器要求保存 RPC 设置的事务内版本条件，直接 REST 更新不能绕过版本检查；不开放删除。
- 函数使用 `SECURITY INVOKER` 和空 `search_path`，没有通过提升权限绕过用户隔离。主键覆盖用户归属查询；RLS 身份查询使用 `(select auth.uid())`。
- 数据库限制快照形状、单份约 1 MiB、每类最多 2,000 条；客户端提前限制 UTF-8 内容不超过 900,000 字节。结构化文字优先，附件不放进 JSON 快照。
- `src/cloud/client.ts`：类型化客户端和 PKCE 会话配置，只接受 HTTPS 与浏览器公开的 `sb_publishable_…` 密钥；没有获取或使用特权密钥。
- `src/cloud/sync-adapter.ts`：读写接口、上传前格式验证、返回完整冲突快照。调用者必须先持久化待同步内容与操作 ID，再发送和重试。
- `src/cloud/journal-validation.ts`：远端内容进入本地前检查格式、日期、金额整数、重复 ID、资金日期和大小，未知版本不能覆盖本地手账。
- `supabase/tests/phase0_journal_sync.sql`：模拟不同数据库角色测试归属、匿名访问、重试、过期版本、非法载荷与直接写入。所有虚构记录在事务末尾回滚，不插入真实认证用户。

客户端适配器尚未连接 `App.tsx` 和本地存储，因此不会自动上传示例或个人内容，也不会把“本地保存”显示成“已同步”。`supabase/config.toml` 是 CLI 的本地开发配置，尚未应用到远端；项目创建后需另行设置远端认证。
