版本：v0.5\

状态：用户已确定先采用 PWA，功能需求与分期已暂定。第 0 期已创建本地 React/TypeScript/Vite 原型，完成构建、本地保存与浏览器离线检查。尚未创建云项目，真实设备安装与同步仍需验证。

## 1. 推荐结论

用户已确定：先采用 **可添加到桌面/主屏幕的 Web App（PWA）+ 免费静态托管 + 托管云数据库**，避免原生 iOS 的安装分发费用，并且不自行部署或运维服务器。

建议组合为 React/TypeScript 客户端、Cloudflare Pages 免费静态托管，以及 Supabase Free 的登录、PostgreSQL 和私有附件存储。Windows 和 iPhone 使用同一份应用与云端数据，分别设计桌面和手机界面。

这一组合的基础规划、感想、收支、手动健康记录和同步，目标是在当前免费额度内实现平台月费 0 元，不需要 Apple 开发者会员或自有服务器。这是基于公开免费政策和个人使用规模的方案判断；实际网络、设备体验和用量仍需验证，不能承诺免费政策永久不变或无限存储。

现阶段统一按 PWA 设计和开发，不需要 Flutter、Xcode 或 Apple 开发者会员。若将来确有原生能力需求，再单独评估原生方案与费用。

## 2. 两种 App 形态的区别与费用

| 方案 | 实际如何使用 | 免费条件与限制 | 建议 |

两种形态都可以认真设计手账视觉、时间轴、感想、记账、资金计算和双端同步。PWA 底层是网页技术，原生 App 底层是手机平台程序；界面美观和主要业务功能不由这个名称决定。区别集中在安装分发、系统接口和后台行为。

## 4. Windows 与 iOS 如何共用

业务层共享目标、预算、资金计算、账单规范化和同步规则。UI 层共用颜色、排版、组件语言和状态语义，同时分别提供合适的布局与操作。

- Windows：宽幅时间轴、详情侧栏、鼠标滚轮、键盘快捷操作和文件导入。
- iPhone：底部主要导航、触摸手势、快速输入、浏览器可用的文件选择、安全区域与字体放大。
- PWA 不能直接调用原生 HealthKit；手动健康数据与报告文件导入可保留，原生健康接入另行评估。

PWA 需要分别验证 Windows 浏览器窗口、安装后的桌面窗口以及 iPhone 主屏幕 Web App。桌面预览或手机尺寸模拟不能代替 iPhone 实测。

### 离线与后台的具体边界

PWA 首次访问与获取云端数据需要联网。成功缓存后，可离线浏览和新增基础记录；同步安排在应用打开、回到前台和网络恢复时执行，不承诺 iPhone 在应用关闭后持续同步。

浏览器存储可能因清理网站数据、设备空间或存储策略而被删除，因此 IndexedDB 是缓存与待同步区，不能被当作永不丢失的唯一备份。尽早同步、清楚提示待同步状态，并保留导出恢复路径。[浏览器存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

若选择原生 iOS，则仍需 macOS/Xcode 构建、签名与真机验证；开发工具免费不意味着设备、构建服务、会员和分发都免费。[Flutter 平台集成](https://docs.flutter.dev/platform-integration)

## 5. 云端同步建议

两端方便地通过互联网同步，需要一个双方都能访问的数据中转服务。推荐“托管云端共享数据 + 本地缓存 + 待同步队列”。服务商运行数据库、认证和接口，用户不租服务器、不安装数据库、不处理操作系统升级。

它仍需要一次性的云项目创建与配置；助手在得到账号授权后完成这些技术工作，并配置后续从 GitHub 自动构建发布。用户需要拥有平台账号、完成本人登录授权，以及在手机上添加应用图标；不需要操作服务器部署命令。

关键技术是同一个人账户、HTTPS 数据接口、共享数据库，以及应用内的同步逻辑。云数据库保存共同数据；电脑写入后手机取回变化；断网时先保存本地，重新打开并联网后补传。Supabase 的实时通知可以加快应用打开时的更新，但不会自动完成离线同步和冲突处理。

```mermaid
flowchart LR
    H[免费静态托管：应用界面] --> W[Windows 客户端]
    H --> I[iPhone 客户端]
    W <--> WL[本地缓存与待同步队列]
    I <--> IL[本地缓存与待同步队列]
    WL <--> A[托管身份验证与数据接口]
    IL <--> A
    A <--> D[免费额度内的共享数据库]
    A <--> S[免费额度内的私有附件存储]
```

实现原则：

- 首次登录并取得数据后，断网仍可浏览缓存和创建基础记录；重新联网后重试同步。
- 记录使用稳定 UUID、账户归属、服务端版本号和修改信息。金额按分存储，计算使用整数或精确十进制，避免浮点累计误差。
- 使用操作 ID 和数据库约束保证重复请求不会创建重复记录。
- 更新以服务端版本校验，不凭客户端时钟判断谁覆盖谁。两端编辑同一条旧版本记录时保留冲突版本，提供明确的处理入口。
- 删除同步带有删除标记，避免另一台离线设备把旧数据重新上传。最终清除与备份保留规则在实现时明确。
- 时间戳统一保存，事件日期另存日期和精度，避免时区转换导致生日、大事记或目标日期偏移。
- 导入记录保留来源和外部交易标识；无交易 ID 时组合字段校验并提示疑似重复，不随意合并相似消费。

数据库启用按用户的行级权限控制；私有附件采用独立访问控制。Supabase 的行级权限需配置和测试，不能只依靠前端筛选用户 ID。[Supabase RLS 文档](https://supabase.com/docs/guides/database/postgres/row-level-security)

### 登录、网络与免费额度验证

Supabase Free 与 Cloudflare Pages 是初步推荐；在用户常用网络和 iPhone 上验证访问、延迟与登录后才确定。若访问不稳定，再寻找同样不需要用户运维的方案，不把“用户要自行部署国内服务器”作为默认退路。

个人版可采用 GitHub 登录，避免把验证码短信和付费邮件服务加入基础方案；应用登录与代码仓库授权分别配置，连接了 Codex 的 GitHub 插件并不等于应用已完成登录集成。Supabase 内置邮件发送存在收件人和速率限制，不能未经验证就承诺所有邮件登录方式免费可用。[GitHub 登录文档](https://supabase.com/docs/guides/auth/social-login/auth-github)、[邮件限制](https://supabase.com/docs/guides/auth/auth-smtp)

云端使用传输保护与服务商存储保护，浏览器端使用受支持的会话管理并限制脚本注入风险；特权密钥不放入客户端。端到端加密另有密钥恢复与查询成本，目前不宣称已实现；健康报告阶段再决定额外的数据保护需求。

Cloudflare Workers/D1 也有免费额度，但需要开发和发布自己的数据接口与权限逻辑，本次保留为替代方案；Firebase 虽有免费数据库额度，文件存储目前要求 Blaze 计费计划，因此不把它列为这次全套免费存储的首选。[D1 免费额度](https://developers.cloudflare.com/d1/platform/pricing/)、[Firebase 存储计费条件](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)

## 6. 支付宝、微信等账单接入

### 已核实的边界

官方公开的 `alipay.data.dataservice.bill.downloadurl.query` 用于获取商户离线账单地址，类型包括商户交易收单和商户账户资金变动。它不能作为“个人授权后即可读取个人全部消费流水”的证据。[官方接口文档](https://developer.alibaba.com/docs/doc.htm?articleId=1054&docType=4&treeId=180)

截至本次公开文档核实，尚未查到可供本项目直接使用、经普通个人授权即可读取其全部消费流水的通用接口。这是目前的核实结果，未来如有正式开放能力可以重新评估。微信和银行渠道也需独立核实，不能从支付宝推断其他平台权限。

唤起支付软件完成付款、查询本应用发起的交易，与读取用户在其他地方的历史消费，是不同的接入需求；本产品当前关注后者。

### 推荐的接入顺序

1. 手动记账：保证日常使用不依赖外部平台权限。
2. 账单文件导入：采用用户当时实际可导出的格式，用样本确认字段、编码、日期、退款和转账规则。
3. iPhone 文件选择导入：减少用户从导出文件到入账的步骤。PWA 接入系统分享菜单作为额外验证项，不承诺自动出现在所有支付软件的分享目标中。
4. 官方个人账单接口：取得明确产品文档和授权资格后再安排实现。

第 2 期只承诺至少一种实际验证过的文件格式。导入流程必须支持预览、校对、幂等和回滚；不把未经确认的数据直接记成消费。

## 7. 健康数据与报告

基础身高、体重和自定义力量记录先手动输入。PWA 保留手动数据与文件导入；若后续选择原生 iOS，HealthKit 可以在用户授权后读取允许的数据类型，但需要启用能力、说明用途并按类型请求权限。[Apple HealthKit 授权说明](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)

后续报告采用分开的阶段：存原文件、识别文本与数值、校对确认、建立历史趋势、辅助解释。PDF/图片识别结果保留原文件位置、单位、参考范围及人工修订；实际医疗意义的解释在实现时核实权威依据。

用户希望双端云同步，因此需设计报告和健康记录在私有托管存储中的访问方式，并控制免费附件额度。若后续进行原生 App 分发或接入 HealthKit，需要复核 Apple 的健康相关审核规则，其中包括不得把个人健康信息存入 iCloud 的规定；不能直接把健康同步改成 CloudKit 存储。[Apple 审核规则 5.1.3](https://developer.apple.com/app-store/review/guidelines/)

若接入第三方报告分析服务，在界面中说明发送哪些内容、存储范围和费用，由用户发起；模型密钥保存在服务端。暂未选定分析提供商，基础版本不依赖模型服务。

## 8. GitHub 的简单使用方式

当前目录已初始化本地 Git，但没有提交，也没有远程地址。GitHub 插件已安装，并通过只读查询确认账号连接可用；本轮文档尚未上传 GitHub，项目远程仓库尚未确定。

后续建议：

- 建一个私有仓库，主分支保存稳定版本；开发使用短期 `codex/` 分支。
- 每个阶段用一个 milestone，需求用少量 issues 管理；小改动小提交。
- 有应用代码后运行格式、静态分析、资金计算测试和 Web 构建，配置托管平台从 GitHub 自动发布；PWA 不需要 macOS runner 或 iOS 签名。若选择原生路线，再配置相应构建。
- 里程碑验收后打版本标签，保留发布说明、可回滚的部署版本，以及所选形态需要的安装说明或安装包。
- 仓库管理需求、代码、数据库迁移和虚构样例。真实账单、体检报告、个人数据库、证书和服务端密钥不入库。

文档与设计决策从一开始纳入版本管理，避免后续开发偏离已审阅的要求。

## 10. v0.2 新增需求的数据与计算规则

### 大事记的文字、分类与等级

事件经过和感想分别保存为独立文本，允许多行与段落，感想可以为空或后续补写；后续若支持富文本，再增加相应结构与迁移，不改变已存的基础文字内容。

分类为独立的用户配置，保存名称、颜色和可选图标，由事件引用；重要程度单独保存，不能从颜色推断。分类配置与事件一起同步，使 Windows 和 iPhone 表达一致。颜色之外保留文字、图标或等级标识，并在多年时间轴上依据等级和节点密度聚合，所有被聚合的事件仍可展开读取。

### 资金账户与资金批次

第一版数据结构需要覆盖：

- 账户及批次的稳定 ID、名称、类型、本金、基准日已结算余额，以及已计提但尚未到账的收益。
- 起息日、到期日或无固定期限、可支取规则、收益率及其适用期间。
- 单利/复利、计息口径、结息周期、收益留存或转出账户，以及到期后的去向和利率假设。
- 分配给目标的基准日资金份额、应急储备和可追加资金设置。

账户用于归集，批次用于描述不同的期限与计息规则。预测从基准日的真实状态开始，不能把此前已结算或已计提的收益再次从起息日完整算入余额。合同类起息信息保留用于计算剩余期间与到期权益。

### 计息与可用性

对于从起息日开始、无中途增减的本金 P，完整 t 年的单利示例为 `P × (1 + r × t)`；按年复利并留存收益的示例为 `P × (1 + r)^t`。这两个式子用于解释完整计息周期，不直接套用到任意支取、利率变化或不完整周期的产品。

年化利率、有效年收益率和结息周期需要保存明确口径：名义年利率按月计息时，月利率为 `r / 12`；有效年收益率换算为等效月收益率时为 `(1 + r)^(1/12) − 1`。等效月收益率用于对应的预测假设，并不表示实际每月结息或可支取。界面可以给出清楚的选项和解释，不能把两种年化数值混为一谈。

复利要求收益重新成为计息基数，不能仅因为每月或每年结息就自动假设复利。官方复利计算工具也分别配置初始金额、追加金额、期限、年化利率和复利频率；本项目在此基础上增加资金可用性与目标分配规则。[Investor.gov 复利工具](https://www.investor.gov/financial-tools-calculators/calculators/compound-interest-calculator)

实际预测按配置的计息区间、结息日、支取日与到期日计算，分别记录预计本息、应计收益、到账收益和可支取金额。到期前的本金是否可取、提前单独支付的利息是否可取，由该批次配置决定；不能从“定期”名称直接推断。

到期可取并不意味着收益继续按原利率增长。到期后转入可用资金池，按设置的后续规则计息；未设置的后续收益率明确为 0%。税费如影响可用收益，需要作为明确的扣减配置；示例计算注明忽略税费，不能宣称已覆盖所有产品的净收益。

### 收入目标求解与防止重复统计

单目标先计算分配给该目标的已有资金在截止日前可支取的本息 E，再计算缺口 `D = max(目标预算 − E, 0)`。对第一版的固定收益假设，在月末追加、资金持续保留至目标日的条件下，记每次新增储蓄到目标日可使用的增长系数为 g，则所需每月追加金额为 `D / Σg`，最后向上取整到分；收益为 0% 时，各次系数为 1，退化为 `D / 月数`。

逐账户的模拟结果用于计算这些系数；已锁定资金、无法在目标日前使用的追加资金或收益不能放入 E 或增长系数。当前资金和新增储蓄分别设置收益规则，不能默认新增资金可以追加到已有定期批次。复杂的提前支取、分段收益与多目标现金流放在第 3 期逐期求解。

预测收益与真实到账记录关联后，采用真实记录替换对应预测，不重复相加。本金在账户间转移、到期释放和收益结转保留关联，锁定池转到可用池不算新增收入；消费发生后降低相应余额与后续收益基数。

### 验证用例

第一版实现时至少验证：50,000 元按 5% 单利满 10 年得到 75,000 元；按年复利得到约 81,444.73 元；未到期且不可支取时不计入提前发生目标的可用资金；200,000 元保持本金完整满一年、按 1% 计息得到 2,000 元收益；中途支出后的收益减少；到期利率不自动续用；0% 收益模型与原简单公式一致；真实到账与预测不重复计入。
